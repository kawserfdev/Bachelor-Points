## 3. Security Analysis

### 3.1 CRITICAL: No Firestore Security Rules

**Finding:** [`firebase.json`](firebase.json) contains no `firestore.rules` reference. There are no security rules deployed. Every collection is open to anonymous read/write.

**Impact:**
- Any user can read/write any document in any collection
- Malicious users can delete/modify other users' data
- No validation on writes (e.g., expense amounts, meal types)
- No authorization on mess membership

**Required Fix:** Deploy comprehensive security rules (see Section in recommended output).

### 3.2 CRITICAL: Google Sign-In Token Bug

**Location:** [`auth_service.dart`](lib/services/auth_service.dart:107-110)

```dart
final OAuthCredential credential = GoogleAuthProvider.credential(
  accessToken: googleAuth.idToken,    // BUG: should be googleAuth.accessToken
  idToken: googleAuth.idToken,
);
```

The `accessToken` parameter is being passed `googleAuth.idToken` instead of `googleAuth.accessToken`. The `GoogleSignInAuthentication` object has both:
- `accessToken` — the OAuth access token
- `idToken` — the OpenID Connect ID token

This means the credential is malformed. Firebase may still accept it in some cases because it only strictly validates the `idToken`, but this is a latent bug that should be fixed.

### 3.3 CRITICAL: Client-Side-Only Authorization

**Every controller** performs role checks on the client:

```dart
// member_controller.dart:36
if (!isAdmin) {
  Get.snackbar('Permission Denied', 'Only admins can change roles.');
  return;
}
```

This is trivially bypassed — a malicious client can call Firestore directly or modify the app. Authorization MUST be enforced in Firestore Security Rules.

### 3.4 HIGH: No Phone Authentication

The user requirement explicitly states:
> Supported Login Methods: Mobile Login

Firebase Phone Auth is not implemented anywhere in the codebase. The `firebase_auth` package is included but no phone sign-in methods exist.

### 3.5 HIGH: Weak Password Policy

[`signup_controller.dart:66`](lib/modules/auth/signup/signup_controller.dart:66):
```dart
if (value.length < 6) { return 'Password must be at least 6 characters'; }
```

No requirements for:
- Uppercase letters
- Numbers
- Special characters
- Minimum length of 8+ (NIST recommendation)

### 3.6 HIGH: Email Verification Not Enforced

[`verify_email_view.dart`](lib/modules/auth/verify_email/verify_email_view.dart) is a dead page. The user can:
1. Sign up
2. See the verify page
3. Click "I have verified, Go to Login" WITHOUT actually verifying
4. Log in normally — no check if `emailVerified == true`

### 3.7 HIGH: Missing Rate Limiting

No rate limiting exists on:
- Login attempts (brute force risk)
- Password reset requests
- Phone OTP requests (when implemented)

Firebase Auth has built-in rate limiting for some operations, but custom Firestore-based rate limiting is needed for:
- Mess creation
- Join attempts
- Expense/meal submissions

### 3.8 HIGH: Missing Security Features

| Feature | Status | Risk |
|---------|--------|------|
| Device Session Tracking | ❌ Not implemented | Cannot detect suspicious logins |
| Login Activity Logs | ❌ Not implemented | No audit trail |
| OTP Expiration | ❌ Not applicable (no phone auth) | N/A |
| User Linking | ❌ Not implemented | Duplicate accounts across providers |
| Admin Protection (MFA) | ❌ Not implemented | Admin accounts not protected |
| Session Persistence | ⚠️ Default Firebase | No explicit configuration |
| Token Refresh Handling | ⚠️ Default Firebase | No explicit handling |

### 3.9 API Key Exposure Risk

[`firebase_options.dart`](lib/firebase_options.dart) contains hardcoded API keys committed to source control. While Firebase API keys are not "secret" (they're designed to be public for client-side use), they should be managed via:
- `google-services.json` (Android) — already in gitignore? NO, it's present
- `GoogleService-Info.plist` (iOS) — already present

The `android/app/google-services.json` IS committed to the repo — this is a configuration file that should remain in the repo for Firebase, so this is actually correct for Firebase projects. However, the `firebase_options.dart` having them duplicated is redundant.

## 4. Firebase Anti-Patterns & Improvements

### 4.1 Getters Creating New Instances

**Location:** Multiple services

```dart
// auth_service.dart:9
FirebaseAuth get _auth => FirebaseAuth.instance;
FirebaseFirestore get _firestore => FirebaseFirestore.instance;
```

While `FirebaseAuth.instance` and `FirebaseFirestore.instance` are singletons internally, using getters like this:
- Adds unnecessary indirection
- Makes it harder to mock in tests
- Should be `final` fields initialized in constructor or `init()`

**Fix:** Store as `late final` fields:
```dart
late final FirebaseAuth _auth;
late final FirebaseFirestore _firestore;

Future<AuthService> init() async {
  _auth = FirebaseAuth.instance;
  _firestore = FirebaseFirestore.instance;
  // ...
}
```

### 4.2 Auth State Changes Driving Navigation

**Location:** [`auth_service.dart`](lib/services/auth_service.dart:18-26)

```dart
_auth.authStateChanges().listen((User? user) async {
  currentUser.value = user;
  if (user != null) {
    await _handleSignIn(user);
  } else {
    Get.offAllNamed(AppRoutes.login);
  }
});
```

This couples the AuthService to GetX navigation. The service should only emit state changes. Navigation should be handled by a dedicated auth guard/governor.

### 4.3 Client-Side Date Filtering

**Location:** [`expense_controller.dart`](lib/modules/expense/expense_controller.dart:67-98), [`meal_controller.dart`](lib/modules/meal/meal_controller.dart:112-146)

All data is streamed from Firestore unfiltered, then filtered client-side with string comparison:
```dart
if (dateStr.compareTo(startDateStr) >= 0 && dateStr.compareTo(endDateStr) <= 0) { ... }
```

This is extremely wasteful:
- All historical data is downloaded to every client
- Filtering is O(n) on the client
- For a mess with 12 months × 30 days × N members of meals, this balloons quickly

**Fix:** Use Firestore `where()` clauses with proper indexes, or store dates as Timestamps and use range queries.

### 4.4 N+1 Query Problem

**Location:** [`report_controller.dart`](lib/modules/report/report_controller.dart:123-150)

```dart
for (var doc in expensesResponse.docs) {
  final profileDoc = await _firestore.collection('profiles').doc(data['created_by']).get();
  // ...
}
for (var doc in depositsResponse.docs) {
  final profileDoc = await _firestore.collection('profiles').doc(data['user_id']).get();
  // ...
}
for (var doc in membersResponse.docs) {
  final profileDoc = await _firestore.collection('profiles').doc(uid).get();
  // ...
}
```

Each loop makes one Firestore read PER ITEM. For 10 members, 50 expenses, 30 deposits = 90 extra reads. This should be batched or denormalized.

### 4.5 No Composite Indexes

The `firebase.json` file has no `firestore.indexes` section. Queries with compound `where()` clauses will fail at scale or generate automatic indexes that need manual approval.

Required indexes (at minimum):
- `meals`: `mess_id` ASC, `date` ASC, `status` ASC
- `expenses`: `mess_id` ASC, `date` ASC, `status` ASC
- `deposits`: `mess_id` ASC, `date` ASC, `status` ASC
- `mess_members`: `mess_id` ASC, `user_id` ASC
- `notifications`: `user_id` ASC, `is_read` ASC, `created_at` DESC

### 4.6 FCM Token Storage Pattern

**Location:** [`fcm_service.dart`](lib/services/fcm_service.dart:56-58)

```dart
await _firestore.collection('profiles').doc(user.uid)
    .set({'fcm_token': token}, SetOptions(merge: true));
```

Problems:
- A user can have multiple devices → multiple tokens
- Storing single token on profile overwrites previous device
- No way to know which device received which notification

**Fix:** Use a subcollection:
```
users/{uid}/fcm_tokens/{token}
```

### 4.7 Date Fields as Strings

Every model stores dates as `YYYY-MM-DD` strings instead of Firestore `Timestamp` objects. This prevents:
- Proper Firestore range queries (string comparison is lexicographic, which happens to work for ISO dates but is fragile)
- Timezone-aware calculations
- Server-side timestamp generation

### 4.8 No Pagination

All list queries are unbounded `.get()` or `.snapshots()`. For a scalable app with 100,000+ users, this will cause:
- High read costs
- Slow client performance
- Memory pressure on devices

Firestore's `limit()`, `startAfter()`, and `orderBy()` must be used with cursor-based pagination.

## 6. Flutter Architecture Issues

### 6.1 GetX vs GoRouter Mismatch

The tech stack specifies **GoRouter** for navigation, but the entire codebase uses **GetX** navigation:

```dart
// Used everywhere:
Get.toNamed(AppRoutes.signup);
Get.offAllNamed(AppRoutes.home);
Get.back();
```

`GetMaterialApp` is used instead of `MaterialApp.router`. Either:
- Migrate to GoRouter as specified, or
- Keep GetX (but the requirement says GoRouter)

### 6.2 No Repository Pattern

Every controller directly accesses `FirebaseFirestore.instance`:

```dart
// In MessController, ExpenseController, MealController, ReportController, etc.
final FirebaseFirestore _firestore = FirebaseFirestore.instance;
await _firestore.collection('messes').add({...});
```

This creates:
- Tight coupling to Firebase
- Impossible to unit test without Firebase emulator
- No abstraction for offline/local-first fallback
- Duplicated query logic across controllers

### 6.3 No Dependency Injection

Services are manually `Get.put()` in order in `initServices()`:

```dart
// main.dart
final storageService = StorageService(); Get.put<StorageService>(storageService);
final authService = AuthService(); Get.put<AuthService>(authService);
// ...
```

No DI container, no interface-based injection, no test mocking support.

### 6.4 God Controller — MessController

[`mess_controller.dart`](lib/modules/mess/mess_controller.dart) handles:
- Fetching user's mess ✅
- Loading mess details ✅
- Listening to member streams ✅
- Profile caching ✅
- Creating mess ❌ (should be separate)
- Joining mess ❌ (should be separate)
- Invite code generation ❌ (should be utility)

### 6.5 Redundant Service — RealtimeService

[`realtime_service.dart`](lib/services/realtime_service.dart) is a pass-through with zero added value:
```dart
Stream<List<Map<String, dynamic>>> streamMeals(String messId) {
  return _firestore.collection('meals').where('mess_id', isEqualTo: messId).snapshots()
      .map((snapshot) => snapshot.docs.map((doc) => {'id': doc.id, ...doc.data()}).toList());
}
```

This should be replaced by a proper **repository** that:
- Maps to typed models
- Handles errors
- Supports offline caching
- Manages subscription lifecycle

### 6.6 Inconsistent Model Patterns

| Model | `fromJson` | `toJson` | Handles Timestamp? | Has copyWith? | Has equality? |
|-------|-----------|----------|---------------------|---------------|---------------|
| `MessModel` | ✅ | ✅ | ✅ | ❌ | ❌ |
| `MemberModel` | ✅ | ❌ | ✅ | ❌ | ❌ |
| `ExpenseModel` | ✅ | ✅ | ✅ | ❌ | ❌ |
| `MealModel` | ✅ | ✅ | ✅ | ❌ | ❌ |
| `DepositModel` | ✅ | ✅ | ✅ | ❌ | ❌ |
| `NotificationModel` | ✅ | ✅ | ✅ | ❌ | ❌ |
| `MessageModel` | ✅ | ✅ | ✅ | ❌ | ❌ |

All models should use `freezed` or at minimum implement `copyWith` and `==`/`hashCode`.

### 6.7 No Error Handling Abstraction

Error handling is ad-hoc `try/catch` + `Get.snackbar` in every controller:

```dart
try {
  await _authService.signIn(email, password);
} catch (e) {
  Get.snackbar('Login Failed', e.toString(), ...);
}
```

No:
- Error type classification
- Retry logic
- Offline detection
- User-friendly error messages mapping

### 6.8 Debug Logging Everywhere

The codebase is littered with `debugPrint` statements — approximately 200+ across all files. This should be replaced with a proper logging framework (e.g., `logger` package) with log levels, or removed for production.

### 7.2 Missing Features in Flow

1. **No Phone Auth flow** — complete missing feature
2. **No Splash/Auth Gate** — `initialRoute` is set to either home or login based on `authService.isLoggedIn`, but there's no loading state while Firebase auth initializes
3. **No session recovery** — if Firebase token expires, no refresh logic
4. **No user linking** — if same user uses email + Google with same email, Firebase automatically links, but the code doesn't handle `account-exists-with-different-credential` errors
5. **No email verification check** — `_handleSignIn` doesn't check `user.emailVerified`

### 7.3 Auth State Persistence

Firebase Auth SDK handles persistence automatically on native platforms. However:
- No `FirebaseAuth.instance.setPersistence(Persistence.LOCAL)` call
- No explicit session timeout
- No forced re-authentication for sensitive operations

## 8. Offline-First Assessment

### 8.1 Current State: ZERO Offline Support

The application has **no offline capabilities whatsoever**:

- Every read hits Firestore directly
- Every write hits Firestore directly
- If network is unavailable, the app crashes or shows errors
- No local database (Isar is mentioned as a requirement but not included in `pubspec.yaml`)
- Firestore's built-in offline persistence is NOT configured

### 8.2 Firestore Offline Persistence (Not Enabled)

Firestore SDK has built-in offline persistence, but it's:
- Not explicitly enabled (`FirebaseFirestore.instance.settings`)
- Not sufficient for the requirements (e.g., "add expense while offline → sync later")
- Limited in conflict resolution capabilities

### 8.3 Required Architecture Per Spec

```
User Action (e.g., Add Expense)
        │
        ▼
  ┌──────────┐
  │  Isar DB  │ ◄── Write immediately
  └────┬─────┘
       │
  ┌────▼──────┐
  │ Sync Queue │ ◄── Add to pending queue
  └────┬──────┘
       │
  ┌────▼──────────┐
  │ Network Monitor │ ◄── Listen for connectivity
  └────┬──────────┘
       │
  ┌────▼──────┐
  │ Firestore  │ ◄── Sync when online
  └───────────┘
```

None of this exists.

## 9. State Management Assessment

### 9.1 Current State: GetX with Inconsistencies

**Dependencies listed in pubspec.yaml:**
- `get: ^4.7.3` — GetX state management
- No Riverpod (requirement says Riverpod)

**Issues:**
1. The requirements document says "Riverpod Providers" but the codebase uses GetX
2. GetX uses mutable state everywhere — no immutability
3. Reactive variables (`.obs`) used inconsistently — some controllers use them, some don't
4. `MessController` holds shared state accessed by multiple controllers (`ExpenseController`, `MealController`, `BalanceController` all `Get.find<MessController>()`) — implicit coupling
5. No state restoration after process death
6. No separation of UI state from domain state

### 9.2 Controller Lifecycle Issues

- `MealController` subscribes to streams in `onInit` but the subscription depends on `MessController.activeMess` being populated — race condition if MealController initializes before MessController
- `ReportController._fetchMessInfoAndData()` makes its own Firestore query to find user's mess instead of using `MessController.activeMess` — duplication

## 10. Database Schema Issues

### 10.1 Stale Supabase Schema

[`database_schema.sql`](database_schema.sql) is a complete Supabase/PostgreSQL schema that is:
- Not used by the current Firebase implementation
- References `auth.users` (Supabase-specific)
- Uses PostgreSQL-specific features (UUID, CHECK constraints, USER-DEFINED types)
- Should be deleted or archived

### 10.2 Role System Limitations

Current roles: `"admin"` and `"viewer"`.

Required roles per spec: `Super Admin`, `Owner`, `Manager`, `Member`.

The current flat role string doesn't support:
- Hierarchical permissions
- Per-mess role differentiation (same user = Manager in Mess A, Member in Mess B)
- Role-based feature access

**Note:** The `mess_members` collection DOES allow per-mess roles since each document is scoped to a (mess_id, user_id) pair. However, the role values are just `"admin"` and `"viewer"` — not the required hierarchy.

### 10.3 User Must Exist in Two Collections

Per spec:
- `users` — core auth identity (maps to Firebase Auth UID)
- `user_profiles` — public profile data

Currently only `profiles` exists, mixing both concerns:
```
profiles/{uid}: { email, full_name, phone_number, fcm_token, avatar_url }
```

This should be split:
```
users/{uid}: { email, created_at, is_active, auth_providers[] }
user_profiles/{uid}: { full_name, phone_number, avatar_url, updated_at }
```

## 11. Extensibility Limitations

### 11.1 Cannot Add New Auth Methods Easily

Adding phone auth requires:
- New methods in `AuthService`
- New UI in `LoginView`/`SignupView`
- New Firestore profile handling
- No abstraction layer to plug in new providers

### 11.2 Cannot Add New Data Sources

If the app needed to support a different backend (REST API, GraphQL), every controller would need rewriting because Firestore is accessed directly.

### 11.3 Cannot Scale Mess Features

Adding features like:
- Bazar schedule management (model exists but no controller/view)
- Mess settings (model exists but no controller/view)
- Monthly summary auto-calculation (table exists but no implementation)
- Subscription/payment tracking

Each requires touching `MessController` (god controller problem) or creating new controllers that duplicate Firestore access patterns.

### 11.4 No Multi-Mess Navigation

[`mess_controller.dart:43-45`](lib/modules/mess/mess_controller.dart:43-45):
```dart
final snapshot = await _firestore.collection('mess_members')
    .where('user_id', isEqualTo: userId).limit(1).get();
```

The `.limit(1)` explicitly prevents a user from being in multiple messes (or at least only loads the first one). Despite the requirement stating "A single user can belong to multiple messes", the current code only supports one active mess at a time.

### 11.5 No Test Infrastructure

- Only [`test/widget_test.dart`](test/widget_test.dart) exists (default Flutter template)
- No unit tests for services
- No unit tests for controllers
- No integration tests
- No Firebase emulator configuration for testing
